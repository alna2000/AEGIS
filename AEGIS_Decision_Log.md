# AEGIS Decision Log

| Decision | Reason |
| --- | --- |
| Use `C:\Python\Projects\AEGIS` as the project root. | Keeps all work in the agreed location. |
| Use FastAPI with Python 3.11 or newer. | Provides a clear, typed foundation with a supported Python baseline. |
| Plan for PostgreSQL without implementing it in this milestone. | Avoids premature data architecture and dependencies. |
| Use pytest and FastAPI's HTTP test client. | Keeps API tests small, deterministic, and independent of external services. |
| Use `pyproject.toml` for package and dependency configuration. | Centralizes modern Python project configuration. |
| Use the project-local `.venv` and point `.vscode/settings.json` to its interpreter. | Keeps the AEGIS Python environment isolated and lets VS Code resolve it even when PowerShell does not visibly show `(.venv)`. |
| Load safe development settings from environment variables and optional `.env`. | Supports local configuration without hard-coded secrets. |
| Exclude `.env` from Git while retaining `.env.example`. | Prevents accidental versioning of local or secret values. |
| Develop and verify locally first. | Keeps the first milestone understandable and deployment-independent. |
| Implement security features phase by phase. | Allows each control to be designed and tested deliberately. |
| Keep the roadmap flexible. | Better learning or security approaches may emerge during the project. |
| Combine a small RBAC capability model with resource-specific ABAC. | Roles remain understandable while clearance, department, compartments, resource policy, and context enforce need-to-know. |
| Use Analyst, Senior Analyst, Supervisor, Security Auditor, and System Administrator as the initial roles. | Covers intelligence work, oversight, independent review, and administration without unnecessary role proliferation. |
| Separate system administration from classified intelligence access. | Enforces least privilege and separation of duties; administrative authority alone cannot read intelligence content. |
| Use four ordered classification levels and one current subject clearance for AEGIS v1. | `UNCLASSIFIED < CONFIDENTIAL < SECRET < TOP SECRET` is deterministic and sufficient for the learning goal without unnecessary real-world complexity. |
| Model each intelligence resource with one or more authorized departments. | Supports explicit cross-department access while ensuring same-department membership is never an automatic grant. |
| Require all listed resource compartments. | An all-required rule provides explicit, deterministic need-to-know behavior that is straightforward to test. |
| Centralize authorization conceptually and default to deny. | Every applicable policy must pass; missing, invalid, ambiguous, stale, or unevaluable policy data cannot produce access. |
| Treat the backend as the authorization boundary and all client state as untrusted. | UI hiding and client-supplied attributes cannot secure direct API access. |
| Normalize users, roles, departments, clearance levels, compartments, and record policy relationships. | Foreign keys and explicit join tables avoid duplicated free-text authorization attributes and make invalid state easier to reject. |
| Keep the v1 role-to-action capability mapping in versioned backend policy rather than a dynamically editable permissions table. | Prevents database content changes from silently redefining authorization and keeps the initial policy small and testable. |
| Treat missing `record_departments` rows as deny and do not support unrestricted-by-department records in AEGIS v1. | Prevents incomplete policy data from becoming an accidental allow. |
| Treat zero `record_compartments` rows as no compartment requirement and require all rows when present. | Gives zero, one, and multiple requirements explicit deterministic semantics while preserving all other checks. |
| Keep current security assignments in normalized tables and preserve changes through append-oriented audit events. | Provides useful v1 provenance without introducing a broad temporal-versioning subsystem. |
| Disable users and retire records/reference data instead of routinely hard-deleting them. | Preserves referential integrity, investigations, and audit context while avoiding dangerous cascades. |
| Store only hashes of reusable session tokens and encrypted recoverable MFA secrets. | A database leak should not expose immediately reusable tokens; TOTP secrets require encryption rather than password hashing. |
| Separate runtime, migration, backup, and administrative database privileges. | The application account can remain least-privileged and must not be a PostgreSQL superuser or schema owner. |
| Keep FastAPI authorization authoritative; consider PostgreSQL RLS only as defense in depth. | Central policy remains consistent across workflows while database controls can later reduce impact without becoming the sole security boundary. |
| Use a new ChatGPT chat for each substantial project phase. | Keeps conversation history manageable while the documented handover package preserves continuity. |
| Require a completion summary, updated current-status handover, and next-phase opening prompt at every phase boundary. | Makes phase transitions repeatable without requiring the user to restate the workflow. |
| Use the local repository and verified GitHub `main` checkpoints as the primary project record. | Git provides synchronized version history; living documents preserve design and handover context. |
| Do not create a full project ZIP for routine phase handover. | ZIPs duplicate Git checkpoints and are reserved for a specific backup, transfer, recovery, direct-access, major-release, or user-requested need. |
| Allow Codex to perform routine phase-end Git/GitHub checkpoint work when authorized. | Saves interactive time while requiring Codex to stop on failed checks, unexpected changes, secrets, conflicts, remote divergence, authentication failures, or rejected pushes. |
| Require explicit approval for force pushes, hard resets, destructive history rewriting, or conflict resolution that could discard work. | Prevents routine automation from damaging recoverable project history or user work. |
| Use SQLAlchemy 2.x typed models and reviewed Alembic migrations for authentication persistence. | Implements the approved PostgreSQL architecture without unmanaged schema mutation. |
| Implement the `users` table incrementally and defer department and clearance foreign keys. | Password authentication does not require Phase 3 authorization reference data; later migrations can extend the same model without replacing it. |
| Canonicalize usernames by trimming, restricting to a documented ASCII syntax, and lowercasing. | Prevents case-only duplicates and avoids surprising Unicode equivalence rules for login identity. |
| Canonicalize optional email by trimming and ASCII-lowercasing the complete address. | Provides one deterministic identity comparison rule and database uniqueness when email is present. |
| Use Argon2id with versioned parameters behind a dedicated password service. | Provides salted, memory-hard password storage, controlled verification failure, and automatic detection of verifiers that need stronger parameters. |
| Require new passwords to contain at least eight Unicode characters and no more than 1024 UTF-8 bytes, without composition rules. | Establishes a small creation-policy baseline, preserves passphrases and Unicode, and bounds unreasonable password-hashing input. Existing valid legacy verifiers remain verifiable even when their password is shorter than the current creation minimum. |
| Treat an account as usable for password authentication only when active and not disabled. | Fails closed at the service boundary before any future HTTP login or session behavior exists. |
| Use SQLite only for isolated deterministic persistence and migration tests. | Tests do not require provisioned infrastructure while PostgreSQL remains the configured application and deployment target. |
| Return one generic login-attempt failure result for wrong credentials, unavailable accounts, and malformed identifiers. | Prevents the future HTTP layer from exposing internal account or credential failure reasons. |
| Verify unavailable accounts against one pre-generated current-parameter Argon2id dummy verifier. | Mitigates the dominant password-processing cost difference without generating a new hash per request or claiming mathematical constant-time behavior. |
| Emit typed, allowlisted `PASSWORD_AUTH_SUCCESS` and `PASSWORD_AUTH_FAILURE` events through an authentication audit sink. | Names the completed fact precisely as password credential verification without implying that a server-side session was durably established. |
| Require credential-verification audit emission and raise a controlled error if the sink fails. | Credential authentication must not complete normally when its required security event was not emitted. |
| Emit successful credential-verification audit before applying a verifier rehash. | An audit failure leaves the old valid verifier unchanged; the caller retains transaction ownership and no repository helper commits independently. |
| Limit authentication request context to a UUID request ID, canonical optional IP address, and bounded optional user agent. | Supports future investigation while preventing arbitrary headers/body data from entering authentication events or influencing identity and authorization. |
| Generate each session credential from 32 cryptographically random bytes and encode it as unpadded URL-safe Base64. | Provides 256 bits of server-selected entropy in an opaque cookie-safe token and prevents client-selected session identifiers from becoming authenticated. |
| Store only a deterministic SHA-256 hash of each high-entropy session token. | Supports efficient indexed lookup while preventing a database leak from directly revealing reusable browser credentials; password hashing is unnecessary for uniformly random 256-bit tokens. |
| Use an eight-hour default session lifetime with an environment-backed 5-minute-to-24-hour configuration bound. | Keeps sessions finite and security-conscious while permitting deliberate local configuration without real-time-dependent tests. |
| Use an `HttpOnly`, `SameSite=Strict`, path-root cookie and require `Secure` outside explicit development/test environments. | Prevents frontend JavaScript access, provides a reviewed CSRF baseline, and preserves local HTTP testability without weakening public defaults. |
| Resolve authentication through one session service that rechecks expiry, revocation, and current user usability on every request. | Prevents endpoints from diverging and immediately denies existing sessions when an account becomes inactive or disabled. |
| Revoke a presented AEGIS session and create fresh server-selected material in the successful login transaction. | Defends against fixation and replaces the browser's prior session without introducing broad multi-device session management. |
| Commit verifier upgrades, prior-session revocation, and new-session persistence before emitting the authentication cookie. | A persistence or commit failure rolls database changes back and cannot produce a successful HTTP login or reusable client credential. |
| Keep credential-verification audit emission required and fail closed when its sink raises. | Session creation cannot proceed after a required credential-audit failure, preserving the Part 2 security policy and enumeration behavior. |
| Treat the current authentication audit sink as non-persistent, non-transactional application logging. | Avoids claiming immutable or PostgreSQL-atomic evidence before persistent audit storage is implemented in its owning later phase. |
| Do not emit session lifecycle events through the current logging sink. | Durable session establishment is represented by committed session state and cookie issuance; deferring session events avoids ambiguous failure semantics and false logging/database atomicity claims. |
| Defer dedicated CSRF tokens while browser state changes are limited to idempotent logout and pre-authentication MFA completion. | `SameSite=Strict` and possession of the current TOTP factor constrain the reviewed completion endpoint, but they are not a universal CSRF design; enrollment and future authenticated state-changing workflows remain blocked pending deliberate protection. |
| Encrypt TOTP secrets with Fernet authenticated encryption using an independently configured URL-safe Base64 32-byte key. | Uses maintained cryptography to provide confidentiality and integrity; no usable key is stored in PostgreSQL, source control, or tracked configuration. |
| Persist a non-secret encryption key ID with each MFA ciphertext. | Allows decryption to fail closed on an unexpected version and establishes a small future key-rotation boundary without committing key material. |
| Use PyOTP with SHA-1, six digits, 30-second steps, and an acceptance window of exactly one adjacent step in either direction. | Matches common authenticator applications while bounding clock skew to +/-30 seconds and keeping deterministic tests sleep-free. |
| Permit only one non-disabled TOTP credential per user and treat generated credentials as pending until confirmation. | A partial unique index prevents conflicting pending/enabled state while preserving disabled credential history and allowing later fresh enrollment. |
| Persist the last accepted TOTP counter and lock the credential row during verification. | Rejects reuse and older counters, permits later valid steps, and prevents concurrent PostgreSQL requests from accepting the same step in normal caller-owned transactions. |
| Emit `TOTP_VERIFICATION_SUCCESS` and `TOTP_VERIFICATION_FAILURE` rather than generic MFA-completion events. | Precisely records factor verification without claiming password-login completion, session issuance, authorization, or classified-resource access. |
| Keep Part 4 TOTP enrollment and verification at the service layer. | Adding authenticated state-changing browser routes before a dedicated CSRF design would widen the reviewed boundary; Part 5 owns safe login integration. |
| Represent password-verified MFA state with a separate 256-bit random bearer challenge and persist only its SHA-256 hash. | A challenge cannot act as a normal session, caller-selected material is rejected, and a database disclosure does not reveal the reusable cookie value. |
| Use a five-minute default MFA challenge lifetime bounded from one through ten minutes. | Keeps password-only state deliberately short while allowing safe configuration and deterministic expiry testing. |
| Store challenge consumption and revocation separately and lock the challenge row during resolution. | Completion is single-use, newer password logins can invalidate older challenges, and PostgreSQL serializes competing completion attempts in the caller-owned transaction. |
| Use a separate `HttpOnly`, `SameSite=Strict`, `/auth`-scoped challenge cookie and require `Secure` outside development/test. | Keeps challenge material out of JSON, URLs, and JavaScript while allowing both the verification and logout routes to consume or revoke it. |
| Commit TOTP replay state, challenge consumption, old-session revocation, and fresh-session creation together before issuing cookies. | A failed database operation cannot return authenticated success, consume the factor counter durably, or issue a normal session credential. |
| Keep password and TOTP verification events precise and omit a synthetic `LOGIN_SUCCESS` logging event. | The current sink is non-persistent and non-transactional; committed session state and cookie issuance remain the only durable login-completion facts. |
| Keep `AuthenticatedPrincipal` identity-only and load a separate immutable `AuthorizationSubject` from current server-side persistence. | Prevents stale or client-controlled role, department, clearance, and compartment data from becoming session authority. |
| Add nullable transitional department and clearance foreign keys to existing users and treat missing assignments as deny. | Existing Phase 2 users must not receive silent authorization defaults; required final-state columns can follow a reviewed assignment/backfill workflow. |
| Seed controlled authorization reference rows with stable public UUIDs in migration `20260822_0005`. | Produces deterministic non-secret policy identifiers without creating users, credentials, assignments, sessions, or records. |
| Keep role capabilities in an explicit version-controlled mapping and require classified-resource ABAC checks after capability. | Capability only permits evaluation to continue; it cannot silently redefine policy or bypass clearance, department, compartments, lifecycle, separation of duties, or future action-specific workflow/context restrictions. |
| Use a content-free typed resource-policy snapshot and a pure fail-closed evaluator before record persistence. | Makes authorization logic independently testable while preventing Part 1 from prematurely introducing classified records or HTTP enforcement. |
| Keep Phase 3 Part 1 authorization decisions side-effect-free and defer persistent authorization auditing. | Internal deny reasons prepare a controlled later audit boundary without misrepresenting the Phase 2 logging sink as durable authorization evidence. |
